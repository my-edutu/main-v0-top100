# Project100 impact groups

The user authorised implementation using our judgment on 31 October 2026. Nigeria uses permanent state groups (including FCT), with local school projects inside each state. International members choose a destination. The six initial destinations are Ethiopia, Ghana, Cameroon, Kenya, Benin and DR Congo. Read-only awardee analysis covered all 1,808 records; after normalising unambiguous spelling, language and city variants, 2026 counts were 63, 42, 39, 32, 27 and 27. Blank and ambiguous country values are not assigned by guessing. These counts describe awardee records, not scholarship recipients.

## Experience

The existing dashboard scholarship card opens an impact overview: the mission, total verified contributions by currency, destination groups and how the project works. Members choose a Nigerian state or one of six countries, join, see their group's plan, supporters and updates, then contribute. Group detail separates raised, recorded spending and remaining funds; project targets describe planned impact, never invented delivered outcomes. Contribution uses a short form: amount, currency, personal or organisation attribution, optional anonymity, review of the destination, hosted checkout, then server confirmation. Further contributions use the same flow. A member can join without paying. Changing groups affects future contributions only.

Members and admins can upload group photos and captions; only members of that group or admins can post. Members can delete their own update; admins can moderate any update. No public upload endpoint or unrestricted image URL is accepted. Uploads use size/type validation, actual image decoding and owned paths. Updates are visible to signed-in members. Supporters show names or organisation attribution according to the contribution's visibility choice; contact details and payment identifiers remain private.

Admin has a Project100 workspace: totals, group selection, contributors, projects with itemised plans and targets, delivered support records with reference/evidence, and group updates. Recording expenditure is bookkeeping of support already delivered, not a bank transfer. Never expose a button that pretends to pay a school. Expenditure cannot exceed the group's confirmed available funds in the same currency. Admin can top up using the member contribution flow, rather than editing a balance.

## Grouping

Permanent geographic groups fit the user's chosen state/project structure; yearly shuffled cohorts were considered but would lose continuity. Existing random application group tables remain untouched. Explicit membership is preserved on repeated grouping. The admin action processes submitted, consenting applications and explicit destination preferences, joining only unassigned members with a determinable state or chosen country. Nigerian locations are matched against the existing canonical state list; conflicting or missing states stay unassigned. International members without a destination stay unassigned until they choose. A stored report explains assigned, already joined and unresolved records. No grouping action changes a financial allocation.

## Payments and persistence

Use additive Supabase tables with RLS and server-only writes, reusing member authentication and authoritative admin roles. Separate membership, groups, projects, contributions, provider events, expenditures and photo updates. Database functions enforce atomic settlement, event idempotency, reservations and expenditure limits. All amounts are safe integer minor units. Persist the destination, amount, currency, name/organisation and privacy choice before opening checkout. Stable request idempotency recovers the same checkout; an intentional top-up gets a new key. Bachs supports raw pricing; NGN is charged in NGN and USD supports provider currency conversion. Display separate NGN/USD totals without combining them. Verify provider checkout, reference, purpose, original amount/currency and successful charge before settlement. Browser callbacks cannot mark paid. Authenticated refund/dispute events freeze affected funds for review and cannot be overwritten by late success. Production activation requires the migration, dedicated Bachs webhook secret/destination and checkout flag; no live collections or production mutations are part of verification.

## Verification

Test canonical country/state selection, repeated grouping, consent and ambiguous records; checkout amount/currency validation and idempotency; signatures, provider retries, mismatch and late success; atomic concurrent expenditure limits; member/admin permissions and image ownership. Render phone and desktop views, test joins/forms/errors with explicit local fixtures, run typecheck, scoped lint, relevant payment regressions and the full suite. Record any production-configuration or authenticated-browser limitations.
