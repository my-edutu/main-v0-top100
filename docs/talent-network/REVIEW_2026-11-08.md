# PR #7: critical implementation review and reliability corrections

**Review input:** `79d2f33747f81b7e2746d059c6049366970c563f` on `feat/talent-discovery-review-20261108`.

**Decision:** keep the PR draft. This is a concrete improvement pass, not a production approval. Main, homepage content, deployment, live data and member sending remain untouched.

## Critique

The first implementation was stronger at adding feature surfaces than at maintaining trustworthy state during ordinary member interactions. A clean-looking screen did not establish safe saving, conflict handling or integrated privacy choices. The orange/amber direction itself was coherent; replacing it would not fix the highest-impact defects.

| Priority | Observed weakness | Correction |
|---|---|---|
| High | A slow profile save replaced text entered after the request started. | Keep the submitted edit generation separate from current inputs. Adopt the saved revision without overwriting newer text; state explicitly what remains unsaved. |
| High | A stale full privacy form could restore permission withdrawn elsewhere. | Require the last confirmed privacy snapshot; compare it atomically under the profile row lock. Conflict responses retain local choices but prohibit silent retries. |
| High | The old all-off operation also submitted a stale email checkbox value. | A dedicated withdrawal action contains no permission grants and preserves the latest saved email preference on the server. |
| High | Overlapping reads could replace newer results; an old read could undo a confirmed write in client state. | Abort superseded reads and use generation checks. Serialize profile/privacy writes within one member workspace. |
| High | Lost authentication left a previously loaded private record in the resource. | Clear private state on 401/403/404 and suppress late state writes after unmount. |
| Medium | The editor embedded an independently loaded privacy copy, making stale state and lost choices more likely. | Reuse one resource and write lock; keep the privacy form mounted across wizard steps. |
| Medium | Editing privacy checkboxes changed the apparent saved record before confirmation. | Separate checkbox drafts from saved state, and show the saved discovery permission and an unsaved indicator. |
| Medium | Duplicate rapid saves and invalid successful HTTP payloads were not handled defensively. | Synchronous write gates, response validation, and explicit unconfirmed-save errors. |
| Medium | Skills input rewrote the value on each comma, and blank entries inflated readiness. | Preserve raw text while typing; normalize at validation and count meaningful fields only. |
| Medium | Review readiness, published versus draft state and navigation were unclear. | Add a field-specific checklist, a clearly labelled unpublished preview, step count, Back navigation and focus movement. |
| Medium | The candidate's first sticky action footer obscured review/privacy content on mobile. | A browser geometry check failed; actions were returned to normal document flow and the check passed. |

## Implemented scope

The changes are confined to the member editor, shared member resource, privacy controls/API, validation, regression harnesses, an unapplied SQL guard, CI checks and release documentation. No existing homepage lines or awardee recognition content were changed in this pass. No additional paid service, dependency upgrade, deployment or live campaign was introduced.

Privacy permission remains separate from recognition history and is not silently enabled. Content review is not a universal verification badge. Profile readiness is not a merit score. Existing public approved snapshots do not automatically change when a draft is saved.

The new member API deliberately does **not** fall back to the old unguarded visibility function when the checked RPC is missing. Local/staging schema setup now has three SQL files; see `LOCAL_REVIEW.md`.
