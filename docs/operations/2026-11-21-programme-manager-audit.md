# 2027 programme manager: audit and release notes

The existing `/admin/events` screen uses `public.events` and `public.event_invitations`; events require an exact start time and have publication and visibility controls. The workbook supplies months rather than confirmed dates. Its 25 activities are therefore separate private planning records, and linking one to an existing event does not create, publish or invite anyone to that event. Existing invitations remain attached to their original event IDs.

The audited branch uses Supabase migrations and has no Prisma schema. Admin routes use `requireAdmin`, which resolves the current profile role from the database. Project100's existing scholarship and impact operations are not replaced. The workbook's Weekly Execution sheet repeats the month in the Programme column rather than identifying an activity, so its 100 rows are not assigned to events. The three explicit first actions are seeded without invented owners or deadlines.

The programme manager includes a programme register, task priorities, editable calendar and event links, partner records, itemized costs and funding, member interest with consent and withdrawal, impact and attendance records, and private weekly snapshots. Approval requires evidence for each essential quote, sufficient received cash or confirmed in-kind support, and evidence for those contributions. Amounts are recorded in integer kobo. Funding received and confirmed in-kind are entered by administrators with evidence references; the application does not independently verify bank receipts or documents. Founder cash contribution is not assumed or seeded.

The worker endpoint produces one replaceable snapshot per Lagos calendar week and does not send messages. Example systemd files are provided but are not installed or enabled. The host/container name and paths in the example must be checked before any later deployment. Apply migrations and enable schedules only on the active Dokploy/self-hosted Supabase environment after the release has been tested and authorised; never use the retired hosted project.

Checks performed in an isolated plain PostgreSQL instance include seeding, approval underfunding, closed member interest, and evidence gates for confirmed partners and verified outcomes. These do not substitute for testing actual Supabase authentication, Data API access, mobile/desktop flows, or the complete production deployment. No production migration, deployment or scheduler change was performed as part of this work.
